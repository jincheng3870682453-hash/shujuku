## 0.1 架构方向决定（2026-10-18，用户裁定）

用户要求做成「真正现代化、有企业级实力」的数据服务项目，并明确同意以下架构决策。

### 双部署形态（同一套核心）

| 维度 | 模式 A · 单机/离线 | 模式 B · 服务器 |
|---|---|---|
| 目标 | 数据不出设备，隐私承诺最硬 | 多用户共享，对外开放端口 |
| 引擎 | SQLite（桌面 / Electron） | PostgreSQL |
| 访问方式 | 本地直接使用 | Nginx + Flask REST API |
| 同步 | **加密 `.drsync` 增量包**，通道由用户自选 | 中心库，天然一致 |
| 载体 | `.exe` / 安装包 | `docker-compose` |

核心（权限 / 审核流 / 字段定义 / RowStore 抽象）**两种模式完全共用**，零改动。

### 引擎选型：弃 MySQL，转 PostgreSQL

**MySQL 出局的理由（硬事实，非偏好）：**
1. MySQL 归属甲骨文（2010 年随 Sun 收购）——与「不向甲骨文付费」的用户诉求直接冲突
2. MySQL 的 JSON 索引**必须建虚拟列 = 每次开索引一次 ALTER**，与 Phase 1 建立的
   「写路径零 DDL」目标正面冲突；PostgreSQL 的 GIN 索引直接作用于 JSONB 列，零 DDL
3. MySQL 的 JSON 支持整体弱于 PostgreSQL（无 `jsonb_path_ops` 等价物、无 GIN）

PostgreSQL License 为类 BSD，无任何公司控制，无卡脖子风险；
PostgreSQL 18 原生 UUIDv7 + 异步 I/O，适配高并发场景。

**不选分布式数据库（TiDB / OceanBase / CockroachDB）的理由：**
本产品是企业内部 HR 数据登记（几百至几万行），非互联网秒杀型负载。
行业已有实证：某银行用 600 台 x86 跑分布式替换 3 节点 RAC，性能提升但运维成本
（人力/电费/机房/备件）大幅增加。分布式当集中式用，综合性能反不如原生集中式。
且它们均为 MySQL 协议兼容，会继承 MySQL 的 JSON 限制。
**结论：应用层代码几乎可平移，等真有秒杀峰值再上分布式。**

### 同步设计：加密增量包（不依赖企业微信 / 不自建服务器）

用户约束：数据敏感、无企业主体、不能开放端口。

**企业微信/个人微信均不可行（已调研）：**
- 个人微信 Web API 自 2017 年后注册账号即无法登录，itchat 已停维护，剩余方案均为逆向协议（随时封号 + 违反条款）
- 企业微信需**企业主体**注册自建应用，用户无主体
- 且两者数据均明文流经腾讯服务器，与「数据敏感」冲突

**定案：`.drsync` 加密增量包 + 用户自选传输通道**
```
A 机生成加密包 → 用户自选通道（U盘/邮件/网盘/微信文件传输助手）→ B 机解密重放
```
- 加密在离开用户硬盘前完成，通道侧只见密文 → 数据敏感 ✓
- 无需企业主体 ✓ 无需开放端口 ✓
- 复用现有 `operations_log` 作变更事件源；复用 `pending_changes` 审核流作冲突仲裁
- 机器少（2–3 台）→ 手工级日同步可接受
- **可选增强**：指定坚果云/OneDrive 文件夹做自动中继（云上仍只有密文）

### 向量检索：本地轻量，不破坏隐私模型

- embedding 与检索**均在用户本地**完成，零外部 API 调用 → 隐私政策零改动
- 轻量模型（如 bge-small-zh 级别），存本地索引
- **后置实施**：在 UUID / PG / 同步三项地基之后
- 论证见 §10.2：本产品数据是结构化筛选型查询（`部门=技术部 AND 在职`），
  非语义语料，向量检索是增强而非刚需

### 主键改造：离线同步的硬阻塞（必须最先做）

离线模式下两台机器各自 `AUTOINCREMENT` 会生成**相同 id**，合并时无法区分记录。
统一改用 **UUIDv7**（时间有序、无碰撞、SQLite 存 TEXT / PostgreSQL 原生支持）。
服务器模式可继续自增 id，但统一 UUID 可让两种模式数据无损互导。

**Phase 2b 实施方案（一次性做到位，用户 2026-10-18 裁定）：**
- `backend/uuid7.py`：零依赖 UUIDv7 生成器（`secrets`+`time`+同毫秒 12-bit 计数器 + 时钟回拨保护，RFC 9562 §5.7）。
- 范围：全部 8 张表的 INTEGER 自增主键 → `TEXT PRIMARY KEY`（应用层生成 UUIDv7）。
- 外键（`pending_changes.row_id/requested_by/reviewed_by`、`audit_log.user_id`、`operations_log.user_id` 等）**类型同步改为 TEXT**，旧整数值迁移为新 UUID（建映射表逐表重写）。
- 路由：`/api/rows/<int:row_id>`、`/api/audit/<int:change_id>`、`/api/users/<int:uid>` → `<row_id>/<change_id>/<uid>` 字符串参数。
- `insert()` 不再调 `get_last_insert_id()`（PG 下本来也不准）；插入前应用层生成 id。
- `session-{user_id}` token 改为 `session-{uuid}`，解析时不再 `int()`。
- 前端 `id: number` → `id: string`（仅类型标注，无逻辑依赖，已确认 21 处可机械迁移）。
- 兼容旧整数 id：迁移期识别纯数字字符串仍当整数查；迁移脚本一次性重写全库。

## 1. 立项依据（调研结论）

调研覆盖 Grist / Baserow / Directus / Salesforce 范式 / PostgreSQL EAV-JSONB 共识，证据如下。

### 1.1 行业现状：无人用 ALTER TABLE 做主存储

| 系统 | 动态字段存储方式 | 出处 |
|---|---|---|
| Baserow | 真实 Postgres 列 `field_{id}` + `Field` 元数据表 + **可配置字段上限** | [models.py `db_column`](https://raw.githubusercontent.com/baserow/baserow/develop/backend/src/baserow/contrib/database/fields/models.py) |
| Grist | 元数据存真实表（`_grist_Tables` / `_grist_Tables_column`），数据由 data engine 管理 | [schema.py](https://github.com/gristlabs/grist-core/blob/main/sandbox/grist/schema.py) |
| Salesforce / 多租户 CRM 范式 | **JSONB `custom` 列 + `custom_fields` 元数据表当 API 契约** | [system-design-answer-fullstack.md](https://raw.githubusercontent.com/evgenyvinnik/llm-driven-system-design/refs/heads/main/salesforce/system-design-answer-fullstack.md) |
| JSONB 建模共识 | JSONB 用于「键集不属于你」的场景；EAV 是「同一个错误决定做得更糟」 | [norm-jsonb-for-open-shapes.md](https://raw.githubusercontent.com/pproenca/dot-skills/refs/heads/master/skills/.experimental/relational-data-modeling/references/norm-jsonb-for-open-shapes.md) |

Baserow 选真实列，但**被迫加了字段数上限设置**（[issue #422](https://gitlab.com/baserow/baserow/-/work_items/422)）——这本身就是对「动态列」路线的承认性让步。

### 1.2 PostgreSQL 的 1600 列硬墙，DROP COLUMN 无法回收

[digoal 实测](https://raw.githubusercontent.com/digoal/blog/49b415f31d8c9c850e1c44e5a35e2295cec6e207/202107/20210729_01.md)：

```sql
-- 加到 1600 列后
alter table c add column c int8;
ERROR:  54011: tables can have at most 1600 columns
alter table c drop column c1;   -- 删一列
ALTER TABLE c
alter table c add column c int8;
ERROR:  54011: tables can have at most 1600 columns   -- 还是不行
vacuum full c;                  -- 连 VACUUM FULL 都没用
alter table c add column c int8;
ERROR:  54011: tables can have at most 1600 columns
```

PostgreSQL 官方限制说明原话：**"Columns that have been dropped from a table also contribute to the maximum column limit."**

Baserow 实际撞墙案例（[issue #3330](https://gitlab.com/baserow/baserow/-/work_items/3330)）：一张表 **10 个活跃列 vs 1590 个已删列**，因为每次字段修改都生成新列、旧列留着做 undo。**一旦触顶，表永久不可修改。**

### 1.3 EAV 与 JSONB 的取舍结论

> **EAV degrades in proportion to how many custom fields appear in one query — which is exactly what power users do.**
> （EAV 的性能衰减恰好与「一次查询用到的自定义字段数」成正比 —— 而这正是重度用户干的事。）

JSONB 路线保留的代价：失去数据库级类型强制。缓解手段：写入路径单一 chokepoint 强制转换 + 后台类型审计。

**本项目不是多租户 SaaS，是单组织内用户自建字段**，键集由本系统用户产生。判据是「能否枚举键」——不可枚举且按用户产生 → JSONB 适用。

## 2. 本项目的具体病灶（逐条对应代码）

### P0-1 物理列只增不减（致命）

`app.py:658` 删除字段：
```python
db.execute_query("DELETE FROM columns_meta WHERE name = ?", (name,))
```
只删元数据，**没有 `ALTER TABLE rows_data DROP COLUMN`**。SQLite 老版本不支持 DROP COLUMN，实际从未执行。

`app.py:359-368` 启动时遍历 `columns_meta` 补列。两者叠加 → **改字段名会产生新的物理列，旧列永久残留，重启也不会回收**。

### P0-1.1 实证：18 个孤儿物理列，数据值被当成列名（2026-10-17 实库取证）

Active 库 `data/app.db`：`columns_meta` 定义 **15** 个字段，`rows_data` 实际有 **35** 列。

定义字段：`工号 姓名 性别 年龄 部门 岗位 学历 籍贯_城市 联系电话 电子邮箱 入职日期 月薪_元 婚姻状况 血型 员工状态`

**不在 `columns_meta` 中的 18 个孤儿列：**
```
人力资源部_员工信息总表   ← Excel 表标题行被当成表头
emp0002                  ← 工号的值
赵子涵                    ← 姓名的值
女                       ← 性别的值
col_49
财务部                    ← 部门的值
出纳                      ← 岗位的值
硕士                      ← 学历的值
天津                      ← 籍贯的值
col_13161559407          ← 手机号被当成列名
赵子涵78_company_com       ← 被破坏的邮箱地址
col_2016_07_03           ← 日期被当成列名
col_23400                ← 月薪被当成列名
未婚                      ← 婚姻状况的值
o                        ← 血型 O 型
在职                      ← 员工状态的值
col_0 / col_1            ← 早期字段残留
```

**根因**：`app.py:491` `_detect_real_header_row()` 把某一行**数据**误判为表头，`app.py:1440` `auto_create_columns()` 随即把该行的每个值当字段名写入 `columns_meta`，并执行
`ALTER TABLE rows_data ADD COLUMN 赵子涵 TEXT`（`app.py:1462`）。之后字段被删（`app.py:658` 只删元数据不删列），物理列永久留下。

**结论**：本项目的 ALTER 路线已经在生产库里留下了不可逆的实物损坏。不是"将来可能出问题"，是"已经坏了"。

另注：`registry.db` 与 `data/app.db` 的 `col_0`/`col_1` 类型分别为 `TEXT/INTEGER` 与 `TEXT/REAL`，两个库的 ALTER 历史已各自漂移，说明初始化补列逻辑（`app.py:373-386`）在不同库上产生了不一致的 schema。

### P0-2 每次写操作都重跑一遍 ALTER

`app.py:853-868`（新增行）、`app.py:1191-1200`（审核回放）、`app.py:1462`（Excel 导入）三处都有「检测缺列 → ALTER 补列」逻辑。写路径上带 DDL，**这是并发写失败和锁竞争的稳定来源**。

### P0-3 表的形状由最终用户决定

`columns_meta` 是用户可写的，`rows_data` 的列由它推导。多用户并发添加字段时，DDL 与 DML 互相阻塞。`_created_by`（权限边界）作为动态列混在业务列里。

### P0-4 类型映射丢失

`app.py:300-303`：
```python
_FIELD_TYPE_MAP = {
    'text': 'VARCHAR(255)', 'number': 'DOUBLE', 'date': 'VARCHAR(255)', ...
}
```
`date` 与 `text` 映射完全相同 → 数据库层无法排序/范围查询；SQLite 无严格类型 → 类型错误静默通过。

### P0-5 审核流是「三天前意图的字符串回放」

`app.py:1135-1221` 靠 `change_type` 字符串分发（`delete` / `delete_column` / `add_column` / `insert` / `update` ...），执行体是从 `new_value` 里 JSON 解出来的**提交时快照**。

- 审批时目标可能已变更（字段被删、被改名），回放照样执行 → **删错对象**
- `app.py:1229` 无论执行成功还是抛异常，都 `UPDATE status='已通过'` → **执行失败的审核也计为通过**
- 提交的密码（`add_user` 的 `new_value.password`）在 `pending_changes` 里存了明文/可还原形式

### P0-6 两张语义重复的日志表

`init_db` 同时建 `audit_log`（`app.py:313`）与 `operations_log`（`app.py:315`），字段几乎一致。而 `clear_logs` 审核类型（`app.py:1132`）允许清空 `operations_log`，与「不可篡改」的宣称矛盾。

## 4. 技术方案

### 4.1 新表结构

```sql
-- rows_data 改为固定列 + JSON 数据区
CREATE TABLE rows_data (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    data      TEXT    NOT NULL DEFAULT '{}',   -- JSONB：{col_name: value, ...}
    created_by TEXT   NOT NULL DEFAULT '',      -- 从动态列提升为系统列
    schema_version INTEGER NOT NULL DEFAULT 1,  -- 数据写入时的 schema 快照号
    created_at DATETIME DEFAULT (CURRENT_TIMESTAMP)
);
-- MySQL: data JSON NOT NULL, created_at DATETIME DEFAULT CURRENT_TIMESTAMP
```

`columns_meta` 保持不变，仍作为字段元数据的唯一事实源；增加 `version` 列用于乐观锁。

### 4.2 索引策略（双引擎）

**SQLite（3.9+ 生成列）**
```sql
-- 只对「被标记为可检索」的字段建索引，避免无界增长
ALTER TABLE rows_data ADD COLUMN f_col_0 TEXT GENERATED ALWAYS AS (json_extract(data, '$.col_0')) VIRTUAL;
CREATE INDEX idx_rows_f_col_0 ON rows_data(f_col_0);
```
新字段不自动建索引；在字段管理页提供「启用索引」开关（写入 `columns_meta.is_indexed`）。

**MySQL 5.7+（虚拟列 + JSON 路径索引）**
```sql
ALTER TABLE rows_data ADD COLUMN f_col_0 VARCHAR(255)
  GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(data, '$.col_0'))) VIRTUAL;
CREATE INDEX idx_rows_f_col_0 ON rows_data(f_col_0);
```

`_created_by` / `created_at` / `schema_version` 是固定列，直接建普通索引。

### 4.3 RowStore 抽象层

新增 `backend/row_store.py`，所有 `rows_data` 读写只经过它：

```python
class RowStore:
    def list_cols(db) -> list[Column]           # 读 columns_meta
    def fetch_rows(db, cols, page, page_size, where, params) -> (rows, total)
    def insert_row(db, data: dict, created_by: str) -> int
    def update_row(db, row_id, data: dict) -> None
    def delete_row(db, row_id) -> None
    def ensure_indexes(db, cols) -> None        # 按 is_indexed 同步生成列
```

好处：`app.py` 的 8 个读写点改成调用 `RowStore`，与 JSON 细节完全隔离；后续若改主意换存储，只动一个文件。

### 4.4 数据迁移脚本 `backend/migrate_jsonb.py`

1. 检出新库是否已迁移（`rows_data` 有 `data` 列？）
2. 读旧表全部列（`get_table_columns`），分出动态列 / `id` / `_created_by`
3. 建新表 `rows_data_new`，按行 `json.dumps({动态列: 值})` 写入

### 4.5 审核流重构（第二优先项）

```sql
CREATE TABLE pending_changes (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    target_kind   TEXT NOT NULL,          -- 'row' | 'column' | 'user' | 'system'
    target_id     INTEGER,
    intent_type   TEXT NOT NULL,          -- 枚举，不再靠字符串分支猜
    payload       TEXT NOT NULL,          -- 结构化意图（不含密码等敏感字段）
    payload_schema_version INTEGER NOT NULL DEFAULT 1,
    base_version  INTEGER NOT NULL,       -- 提交时目标对象的 version
    requested_by  INTEGER NOT NULL,
    status        TEXT NOT NULL DEFAULT 'pending',
    reviewed_by   INTEGER,
    review_comment TEXT,
    created_at    DATETIME,
    reviewed_at   DATETIME
);
```

审批逻辑：
1. 读目标对象**当前** version，与 `base_version` 比对
2. 不一致 → 返回 409 `{"error": "目标已被其他操作修改，请刷新后重新提交"}`，`status` 置 `conflict`（不占 `status` 的三个值）
3. 一致 → 走与直接执行**同一套** service 函数（消除 `api_approve` 里那 90 行重复实现）
4. 执行成功才 `UPDATE status='approved'`；失败置 `failed` 并记录原因

### Phase 2a ✅ 已完成（2026-10-18）事务边界 + 审核原子性

**动机**：立项书 P0-5 记录的真 bug 仍在生产代码中生效——

后果：业务操作失败时，审核员收到"已通过"，而数据实际没变。

#### 新增 `DatabaseAdapter.transaction()`

放在**基类**，两个引擎各自实现底层钩子：

| 方法 | 基类 | SQLiteAdapter | MySQLAdapter |
|---|---|---|---|
| `transaction()` | 上下文管理器，嵌套安全 | 继承 | 继承 |
| `_in_transaction()` | `_tx_depth > 0` | 继承 | 继承 |
| `_begin_transaction_impl()` | no-op | `execute("BEGIN")` | 确保连接 |
| `_commit_transaction_impl()` | no-op | `execute("COMMIT")` | `conn.commit()` |
| `_rollback_transaction_impl()` | no-op | `execute("ROLLBACK")` | `conn.rollback()` |

关键点：
- `execute_query` 在事务内**不再单独 commit**，收尾权交给最外层
- 嵌套只增加深度，真正事务由最外层控制；内层异常传导到外层统一回滚
- 不进入上下文时行为与改造前**完全一致**（向后兼容）

**踩坑记录（两个都由测试逼出）**：
1. SQLite 连接是 `isolation_level=None`（autocommit）。此模式下
   `conn.commit()` / `conn.rollback()` **是 no-op**，必须 `execute("COMMIT")` /
   `execute("ROLLBACK")` 才生效。首次实现用了前者，事务静默失效、数据照样落库。
2. 首次把 `transaction()` 误插进 `SQLiteAdapter`，导致 MySQL 侧**根本没有这个方法**。
   已上移到基类，MySQL 复用同一套嵌套逻辑、只覆写三个底层钩子。

#### `api_approve` 的修复

- 「执行业务 + 写操作日志 + 改审核状态」整体包进 `with db.transaction()`
- 删掉 3 处吞异常的 `except`（`insert` / `update` / `add_column` 分支）——
  它们会让事务感知不到失败，从而仍标记为已通过
- 失败时 `return 500` 并回滚，`pending_changes.status` 保持「待审核」

两台机器各自 `AUTOINCREMENT` 会生成**相同 id**，合并时无法区分记录。主键必须
全局唯一、可离线生成、且按时间有序（避免随机主键把 B-Tree 写散）。

选型：**UUIDv7（RFC 9562 §5.7）**，`backend/uuid7.py`。前 48 位是毫秒时间戳
→ 字符串序 = 时间序，`ORDER BY id DESC` 直接等于「最新在前」，列表页零改动；
同毫秒内 12 位计数器保证严格递增；时钟回拨沿用上次时间戳，绝不回退。

#### 三条写路径（先钉死，再动手）

| # | 路径 | 改造前 | 改造后 |
|---|---|---|---|
| 1 | `DatabaseAdapter.insert()` | INSERT → `get_last_insert_id()` 回读 | 应用层先生成 id，随 INSERT 写入，返回 `str` |
| 2 | `RowStore.insert_row()` | INSERT → `int(db.get_last_insert_id())` | `new_row_id()` → INSERT 带 id，返回 `str` |
| 3 | `app.py` 13 处 `SELECT last_insert_rowid()` | 插入后回读自增 id | 全部改 `db.insert(table, {...})`，直接拿返回值 |

删除整套自增回读设施：`get_last_insert_id_sql()` / `get_last_insert_id()` /
`get_auto_increment_sql()`（→ `get_primary_key_sql()`）。理由不只是「离线撞号」：
MySQL 的 `LAST_INSERT_ID()` 与 PostgreSQL 的 `lastval()` **都绑定连接**，
连接池复用或并发下回读到的未必是刚插入那一行。

#### 主键与外键 DDL

- 8 张表（`users` / `columns_meta` / `rows_data` / `pending_changes` /
  `operations_log` / `audit_log` / `backups` / `ai_analysis_history`）
  `id TEXT PRIMARY KEY`
- 所有引用主键的列同步改 TEXT：`audit_log.user_id`、`operations_log.user_id`、
  `pending_changes.row_id / requested_by / reviewed_by`、`ai_analysis_history.user_id`
- `system_config.key` 本来就是 VARCHAR 主键，不动
- 路由：6 处 `<int:...>` → `<string:...>`（`/api/rows/<row_id>` PUT/DELETE、
  `/api/audit/<change_id>/approve|reject`、`/api/users/<uid>` PUT/DELETE）
- session token：`session-<uuid>`，`restore_session_from_token()` 去掉 `int()` 转换
  （原来的 `int()` 会把合法 uuid 抛 `ValueError`，导致 Bearer token 恢复登录态静默失效）
- 前端：`types/data.ts` 的 `id` / `row_id` / `requested_by` / `reviewed_by` /
  `user_id` 全部 `string`，`tsc --noEmit` 干净

#### 迁移脚本 `backend/migrate_uuid7.py`

与 `migrate_jsonb.py` 同构的安全策略：**两遍搬运 + 旧表保留 + 幂等 + 可校验**。

1. 第一遍为 8 张表所有旧整数 id 生成 `old_int → uuid7` 映射（各自独立命名空间）
2. 第二遍建 `<表>_new`，逐行搬运：id 换 uuid、FK 按映射改写、多态列
   （`pending_changes.row_id` 按 `change_type`、`operations_log.target_id` /
   `audit_log.target_id` 按 `target_type`）分别映射、JSON 里内嵌的 `{"id": int}`
   递归改写
3. 行数校验 → **悬空 FK 修复** → 悬空复查 → 逐表原子改名，旧表保留为
   `<表>_uuid_legacy_<时间戳>`
4. 支持 `--dry-run` / `--verify-only`；重复执行返回 `already-migrated`

**悬空 FK 的处理（本次实测踩到）**：live 库存在历史脏值——
`operations_log.user_id = 99999`（用户早被删）、29 条 `target_id` 指向已删除的行。
这类行本身是有效留痕，不该因一个失效引用阻断整库迁移。策略改为
**置 NULL + 记录 `repaired_fks`**：行保住、引用断掉；置 NULL 后仍有悬空
（说明是映射 bug 而非脏数据）才中止并保留旧表。

#### 踩坑记录（全部由实测逼出）

1. **SQLite `INTEGER PRIMARY KEY` 拒收 uuid 字符串**：新代码跑在未迁移的旧库上
   报 `datatype mismatch`。这不是 bug，而是**上线顺序契约**——必须先迁库再切代码
   （见下方 runbook）。
2. **`migrate_jsonb` 与 `migrate_uuid7` 表名撞车**：两者都用
   `%Y%m%d_%H%M%S` 时间戳，同一秒内先后执行时 `rows_data_legacy_<同一秒>` 重名，
   `ALTER TABLE RENAME` 直接失败。修复：uuid7 用独立前缀 `_uuid_legacy_`，
   并在改名前做同名探测（已存在则追加 `_2/_3`），绝不覆盖已有备份表。
3. **MySQL 不允许 TEXT 直接做主键**（必须有前缀长度）。`id TEXT PRIMARY KEY`
   在 MySQL 方言下自动转 `VARCHAR(36) PRIMARY KEY`（UUIDv7 定长 36）。
4. **GBK 控制台编码不了 `⚠`**：`init_db()` 里的告警打印在中文 Windows 控制台
   抛 `UnicodeEncodeError`，直接让启动崩溃。改为 `[WARN]` 纯 ASCII 标记。
5. `db_adapter.py` 里 `MySQLAdapter.convert_create_table_sql` 原本**定义了两遍**
   （后一个静默覆盖前一个）。硬切时一并清掉重复定义，避免改了一处却不生效。

### Phase 2c ✅ 已完成（2026-11-07）乐观锁：并发编辑返回 409

**动机**（立项书 §4.5 / G6 验收）：「用户 A 打开编辑框 → 用户 B 已改并保存 →
A 才提交」时，A 必须收到冲突提示，而不是静默覆盖 B 的改动。

**实现：`updated_at` 当版本号，SQL 条件里比对（无独立 version 列）**

| 层 | 改动 |
|---|---|
| `RowStore.update_row` | 新增 `base_updated_at` 参数 → `WHERE ... AND updated_at = ?`；0 行受影响即版本过期 |
| `RowStore.get_updated_at` | 读单行版本号，与 `update_row` 构成「读版本→带版本提交」闭环 |
| `RowStore` 时间戳 | `datetime('now')` 只有**秒精度**，同秒内连改两次版本号不变（实测踩到）→ 升为 `strftime('...%f','now')` 毫秒；MySQL 方言自动转 `NOW(3)` |
| `GET /api/rows` | 每行附 `updated_at` 一并下发 |
| `PUT /api/rows/<id>` | 接受 `base_updated_at`；版本过期返回 **409** `{"error": "目标已被其他操作修改，请刷新后重新提交", "conflict": true}`；区分 404（行没了）与 409（被抢先） |
| 前端 DataTable | 行内编辑自动带回 `base_updated_at`；收到 409 提示并自动刷新列表 |
| 兼容性 | 不带 `base_updated_at` 的调用按原行为处理（旧客户端不阻断） |

乐观锁与 `json_set` 原子合并**并存且互补**：不同字段并发写由原子合并保护（都不丢），
同一字段并发写由版本比对仲裁（后提交者收到 409）。

**测试**：`backend/test_row_store.py` 4 个单元用例（同版本成功 / 过期版本 0 行且 B 的值完好 /
合并+锁并存 / 缺行返回 None）+ `backend/test_optimistic_lock.py` 4 个 API 端到端
（先改 A 成功 → B 带旧版本 409 → A 的值完好 / 新鲜版本连续提交 / 旧客户端兼容）。

### Phase 4 ✅ 已完成（2026-11-07）`.drsync` 加密同步 + 局域网 P2P 去中心化

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| JSONB 查询不支持 SQL 排序/分组 | 统计页排序 | 生成列 + 索引；SQLite 用 `json_extract` 表达式排序 |
| MySQL 虚拟列有数量上限 | 字段极多时 | 仅对用户显式开索引的字段建生成列 |
| SQLite 老版本（<3.9）不支持生成列 | 索引方案失效 | 降级为表达式索引 `CREATE INDEX ... ON rows_data(json_extract(...))`，SQLite 支持表达式索引 |
| 迁移中数据损坏 | 极高 | 只读旧表、写新表、保留 legacy 表；迁移前后做 count + checksum 比对 |
| 大盘改动引入回归 | 中 | 分阶段、每阶段独立验证 |
